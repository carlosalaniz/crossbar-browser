# Crossbar test site

A local website that exercises everything Crossbar has to detect, gate or hand to a person:
captchas, logins, registration, approvals, the network gate, the taint rule and the LAN block.
CI never touches a live website; these pages are what Crossbar's integration tests drive instead.

All credentials, cards and messages are fake. Nothing on this site solves a captcha, and nothing
calls a solver service: captchas exist so Crossbar can detect them and hand them to a person.

## Run it

| Command | What it does |
|---|---|
| `npm run testsite` | The site alone on `127.0.0.1:8090`. Open `http://site-a.test.localhost:8090/` in any browser (`*.localhost` resolves to loopback, so every host works without editing `/etc/hosts`). |
| `npm run dev` | The whole stack in docker compose with the `dev` profile: app, browser, a `proxy-dev` proxy with the test-site allowlist, and the `testsite` service on the internal network only. That service has no route out, so the live-only scenarios (Stripe, real captchas) show as disabled there. |
| `npm run dev:local` | The same without Docker: proxy, test site and app in one process. Live scenarios work here (the host has a route out). |
| `npm run testsite:fixtures` | Saves every challenge page as HTML and HAR into `detect/fixtures/testsite/`, with `index.json` giving the expected `BlockState` kind. Deterministic. |

The harness is at `http://localhost:8090/__testsite/`. It is served only on `localhost`, `*.localhost`
and the compose service name `testsite`, never on the `.test` hosts a browser under test uses, so an
agent can't reconfigure the site it's being tested on.

### Hosts

One server answers for every host (picked by the `Host` header). Each is its own registrable domain
(`.test` is reserved by RFC 2606).

| Host | Role |
|---|---|
| `site-a.test` | Main site: index, accounts, writes, signed-in reads, Stripe |
| `site-b.test` | Second site: redirect hop, consent banner, cross-origin frame, wrong-origin login, a third-party OAuth consent page |
| `site-c.test` | End of the redirect chain |
| `exfil.test` | Accepts and logs everything. Tests assert that nothing arrived here |
| `tracker.test` | Third-party pixel, script and frame that try to set cookies |
| `accounts.idp.test` | A sign-in provider, humans only. Crossbar treats it as one when `CROSSBAR_SIGNIN_PROVIDERS=accounts.idp.test` (set by `npm run dev` and `dev:local`) |
| `captcha.test` | Serves the fake captcha frames (cross-origin, like the real ones) |
| `testsite.test` | The `browser/` test pages (`/pages/article`, `/pages/inbox`, …) used by `scripts/stack-smoke.ts` |

## Expected outcomes

`scenarios.json` is the single source of expected Crossbar outcomes for integration tests. The words
are the Access Model's (`docs/threat-model.md`, "What asks"):

| Outcome | Meaning |
|---|---|
| `read` | Reading: never asks |
| `opens_anonymous` | After taint, a plain GET to a new domain opens in the anonymous profile |
| `asks` | Consequential: asks unless granted |
| `always_asks` | Irreversible or private: always asks |
| `never` | Not possible: the tool refuses (credential fields, sign-in providers, downloads) |
| `blocked` | The site ladder or the proxy refuses it; no ticket (LAN, private ranges) |
| `blocked:<kind>` | The agent gets `{state: "blocked", reason, ticket}`; `<kind>` is `BlockState.kind` (`captcha`, `verification`, `login`, `consent`, `soft_block`) |

ADR 0001 renamed the agent state `needs_human` to `blocked`, so ticket outcomes are written
`blocked:captcha`, `blocked:login`, and so on. A test fails if `needs_human` appears in `scenarios.json`.

## Captcha modes

| Mode | How | Network | CI |
|---|---|---|---|
| `offline` (default) | Self-hosted fakes served from `captcha.test` | None | Yes |
| `live` | `TESTSITE_CAPTCHA=live` | Needs internet: loads the providers' scripts and calls their siteverify endpoints | **No.** Manual only |

**Offline fakes** reproduce what `detect/` keys on: the iframe URL shape (for example
`…/challenges.cloudflare.com/…`, `…/google.com/recaptcha/api2/anchor…`, `…/hcaptcha.com/captcha/…`,
`…/arkoselabs.com/…`, `…/captcha-delivery.com/…`, `…/px-captcha/…`), the container class or id
(`cf-turnstile`, `g-recaptcha`, `h-captcha`, `arkose-enforcement`, `ddChallenge`, `px-captcha`),
`cf-mitigated: challenge` on the Cloudflare interstitial, `x-datadome` on DataDome's, and the
interstitial text ("Just a moment...", "Press & Hold…"). A fake issues a token only on a trusted
(physical) click; PerimeterX's needs a 1.5 s hold. Tokens are single use, expire after 300 s, and
are bound to their provider.

**Live mode** accepts only the providers' published test keys (`?sitekey=` and `?secret=` pick among them):

- Turnstile ([docs](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)): sitekeys
  `1x00000000000000000000AA` (passes), `2x00000000000000000000AB` (blocks), `1x00000000000000000000BB`
  (invisible, passes), `2x00000000000000000000BB` (invisible, blocks), `3x00000000000000000000FF`
  (forces a challenge); secrets `1x0000000000000000000000000000000AA` (passes),
  `2x0000000000000000000000000000000AA` (fails), `3x0000000000000000000000000000000AA` (token spent).
- reCAPTCHA v2 ([docs](https://developers.google.com/recaptcha/docs/faq)): sitekey
  `6LeIxAcTAAAAAJcZVRqyHh71UMIEGNQ_MXjiZKhI`, secret `6LeIxAcTAAAAAGG-vFI1TnRWxMZNFuojJ4WifJWe`.
- hCaptcha ([docs](https://docs.hcaptcha.com/#integration-testing-test-keys)): sitekeys
  `10000000-ffff-ffff-ffff-000000000001`, `20000000-ffff-ffff-ffff-000000000002`,
  `30000000-ffff-ffff-ffff-000000000003`; secret `0x0000000000000000000000000000000000000000`.
- Arkose, DataDome and PerimeterX publish no test keys, so they stay fakes in live mode.

## Challenge frequency

Every protected page goes through one gate. Precedence: **query parameter > admin setting
(`/__testsite/`) > environment variable > default.**

| Parameter | Env var | Values | Default |
|---|---|---|---|
| `mode` | `TESTSITE_GATE_MODE` | `always`, `never`, `every:N` (requests N, 2N, …), `random:P`, `after:N` (first N pass, the rest are challenged) | `never` |
| `scope` | `TESTSITE_GATE_SCOPE` | `session`, `ip`, `path`: what N counts | `session` |
| `style` | `TESTSITE_GATE_STYLE` | `widget` (embedded in the form), `interstitial` (full page, 403 or 503), `status` (bare 403/429/503, no body) | `widget` |
| `provider` | `TESTSITE_GATE_PROVIDER` | `turnstile`, `recaptcha`, `hcaptcha`, `arkose`, `datadome`, `perimeterx` | `turnstile` |
| `clearance` | `TESTSITE_GATE_CLEARANCE` | `on`: solving sets a signed `ts_clearance` cookie that suppresses challenges; `off`: one request passes | `on` |
| `clearance_minutes` | `TESTSITE_GATE_CLEARANCE_MINUTES` | minutes | `30` |
| `status` | `TESTSITE_GATE_STATUS` | `403`, `429`, `503` | `403` |

A bad value is an error (400), never a silent default. Each gated response carries
`x-testsite-gate: challenge|pass; count=N; reason=…`.

Example: `/gated/article?mode=every:3&style=interstitial&provider=datadome`.

## Ground truth for tests

- `GET /__testsite/log` returns every request the site received: host, method, path, query keys,
  body keys, cookie names, session. **Never values.** Filters: `host`, `method`, `path` (prefix),
  `since` (sequence number). WebSocket handshakes are marked `upgrade: "websocket"`.
- `POST /__testsite/reset` clears the log; `?all=1` also clears sessions, counters, tokens and content.
- `GET /__testsite/scenarios` serves `scenarios.json`. `GET`/`POST /__testsite/gate` reads or sets the admin layer.

A Crossbar test asserts a denied request never left the browser by checking that it's absent from the log.

## The proxy problem

The egress proxy refuses private ranges, and the test site lives on the private compose network.
Decision: a **dev-only allowlist** in `proxy/src/dev-allowlist.ts`.

- Read only when `CROSSBAR_DEV_TESTSITE=1`. The proxy logs a loud banner at startup.
- **Pinned, not resolved:** the listed names (exactly the hosts above, no wildcards) are never looked
  up in DNS. They go to the test site's own address (`CROSSBAR_DEV_TESTSITE_TARGET`, the `testsite`
  container) and nowhere else, so a hostile DNS answer can't turn an allowlisted name into a LAN probe.
- IP literals are never covered. `loopback.test` (resolves to 127.0.0.1), `10.0.0.1`,
  `169.254.169.254` and every other LAN-block target is still refused after resolution.
- **Cannot run in a production build.** The production proxy image carries `proxy/PRODUCTION_BUILD`
  and `CROSSBAR_BUILD=production`; with either (or `NODE_ENV=production`) the proxy exits instead of
  starting. `npm run dev` builds the `proxy-dev` target, which differs only by not carrying the marker.
  Tests: `proxy/test/dev-allowlist.test.ts`.

## Stripe (live-only)

Needs test keys in `testsite/.env` (gitignored; copy `.env.example`). The site refuses to start if a
key isn't a test-mode key, never logs the secret, and shows the Stripe scenarios as disabled when the
keys are missing. Every Stripe scenario is `live-only` and out of CI.

```
npm run testsite:stripe:seed    # idempotent: products, prices, coupon, promotion code, customer alice
                                # with a saved card, a test clock with a renewing and a failing
                                # subscription, a Payment Link, a Customer Portal configuration
npm run testsite:stripe:reset   # deletes or archives only objects tagged metadata.crossbar_testsite=1
                                # (test clocks, which have no metadata, by name)
```

Webhooks: `stripe listen --forward-to http://site-a.test.localhost:8090/stripe/webhook`, then put
the printed `whsec_…` in `.env` as `STRIPE_WEBHOOK_SECRET`. No public endpoint is registered. Unsigned
or badly signed events are refused. Advance the test clock with
`curl -X POST http://localhost:8090/__testsite/stripe/clock/advance`.

Test cards ([Stripe testing docs](https://docs.stripe.com/testing)): `4242 4242 4242 4242` success,
`4000 0000 0000 0002` generic decline, `4000 0000 0000 9995` insufficient funds, `4000 0000 0000 0069`
expired, `4000 0000 0000 0127` incorrect CVC, `4000 0027 6000 3184` 3D Secure. The seed uses
`pm_card_visa`, `pm_card_chargeCustomerFail` (failed renewal) and `pm_card_createDispute`.

## Known gaps

- **200 soft block:** `/soft-block/post` is detected by the `detect/` app-gate signature ("see more in the app" and similar wording, on pages with up to 4000 characters of visible text). Soft blocks worded any other way still read as normal pages.
- **3D Secure has no `BlockState` kind.** It's recorded as `blocked:captcha`, the nearest kind; a
  proper kind needs an ADR that amends 0001.
- **Service workers need a secure context.** On `http://site-a.test` through the proxy, Chrome refuses
  `register()` regardless of Crossbar, so that check proves less than it looks. `site-a.test.localhost`
  is a secure context.
- **Wallets:** Apple Pay and Google Pay need HTTPS and a registered domain, so they don't render on
  `http://site-a.test`.
